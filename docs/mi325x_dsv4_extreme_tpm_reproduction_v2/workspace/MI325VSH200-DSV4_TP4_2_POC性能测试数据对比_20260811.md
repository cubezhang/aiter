| **九、POC 公平性检查项** | **当前观察** | **潜在影响** | **建议口径** |
|---|---|---|---|
| 容器/实例数量 | H200 微信中明确为 2 容器 TP4；MI325 应在正式报告中同步写明 | 若实例数或 GPU 绑定方式不同，TPM 不能直接横比 | 报告中同时列出 `GPU 数 / TP / 容器数 / 每容器 GPU 映射` |
| 输入长度 | 6,137 vs 6,063，差异较小 | 影响较低 | 可视为基本接近 |
| 输出长度 | 1,110 vs 1,022，差异约 8.6% | 会改变解码负载和总 TPM | 正式对比建议固定目标输出长度或按长度区间分桶 |
| TTFT | MI325 约 25.6 ms；H200 约 471.1 ms | 可能存在 Prefix Cache、请求复用或计时实现差异 | 必须确认 Cache、Prompt 去重、Warmup、流式首 token 定义 |
| 测试持续时间 | 各截图请求数差异很大 | 短跑可能受 warmup、瞬时抖动影响 | 正式 POC 使用固定持续时间并取稳态窗口 |
| Fail Ratio | 7/31 49.86 万轮次有 0.1% 失败；当前为 0 | 高负载下稳定性可能影响有效吞吐 | TPM 必须同时绑定 Fail Ratio 门槛 |
| 输出超长轮次 | 34.81 万轮次平均输出达 2,183.57 tokens | 与后续约 1,100-token 轮次负载不一致 | 该轮次只用于展示调优轨迹，不作为最终横向基线 |
| TPM 展示单位 | 截图数值如 112.51、138.39，微信口径称为 112 万、138 万 | 单位误读会造成 10,000 倍量级错误 | 对外统一写成“万 tokens/min”并同时给完整数值 |
